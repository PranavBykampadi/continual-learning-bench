# Authoring a ticket

A ticket is a directory `orgs/parcelo/tickets/NN_slug/` with four parts. `01_cancel_shipment` is the reference example.

- `ticket.json` has `id`, `title`, `snapshot` (`a`, `b` or `c`), `conventions`, and `body`.
- `hidden/test_ci.py` holds functional tests. `hidden/test_conv.py` holds one test per listed convention, named `test_conv_<convention id>`.
- `gold/` is an overlay of full files that solves the ticket and follows every team convention.
- `naive/` is an overlay that solves the ticket the way the older code in the repo does. It passes CI and breaks every listed convention.

Snapshot `a` is `orgs/parcelo/seed`. Snapshot `b` is `orgs/parcelo/seed` with `orgs/parcelo/migration` copied over it. Snapshot `c` is snapshot `b` with `orgs/parcelo/migration2` copied over it. Overlay files are full files, so start each from the snapshot's version. `docs/api.md` exists from snapshot `b` on, `CHANGELOG.md` differs between `b` and `c`.

## Rules

1. The body reads like a real ticket from a teammate. It states behavior, the file, and the function signature. It never states or hints at a convention. It never names `Money`, `clock`, `DomainError`, `audit`, `events`, `ids.new_id`, the changelog, `settings`, `docs/api.md`, or where tests go. It never says what happens when an operation is repeated on an entity that is already in the target state, and it never says how a returned list is ordered.
2. For a ticket that lists `no_legacy`, the body mentions that an existing helper in `parcelo/legacy/billing.py` has the same logic or numbers, the way a teammate would. The naive solution imports it. The gold solution reimplements it.
3. CI tests accept both the convention-following and the legacy style. Use `pytest.raises(Exception)` for failures. Read amounts through `checks.dollars(value)`. Never assert on audit, events, id format, or time source in `test_ci.py`.
4. Each convention test fails on the naive solution and passes on the gold one. Use the helpers in `orgs/parcelo/hidden_support/checks.py` where one fits (`assert_changelog`, `assert_changelog_v2`, `assert_new_unit_test`, `assert_no_legacy_imports`, `assert_no_direct_time`, `assert_no_uuid`, `assert_api_doc`, `assert_settings`). Check `money` with `isinstance(result, Money)`. Check `clock` by freezing time with `clock.set_fixed(...)` and comparing the stored value, plus `assert_no_direct_time`. Check `ids` by matching `^<prefix>_\d{6}$` on some lowercase prefix, plus `assert_no_uuid`. Check `audit` and `events` by the log growing with the changed entity's id as `entity_id`. The `events` test also asserts that `audit.LOG` did not grow.
   - `changelog` is `assert_changelog("<TICKET-ID>")`, for snapshots `a` and `b`. Tickets on snapshot `c` list `changelog2` instead, checked with `assert_changelog_v2("<TICKET-ID>")`, which wants `- [TICKET-ID] area: what changed`. The naive solution for a `c` ticket writes the old `- area: what changed (TICKET-ID)` bullet, because that is what the neighbouring bullets look like.
   - `sorted` needs a function that returns a list of entities. The test puts entities straight into `db` under ids that are out of order (for example `shp_000009`, `shp_000002`, `shp_000005`, plus a decoy that must be filtered out) and asserts the returned ids equal the expected ascending list. Do not rely on `ids.new_id` here, its counter makes storage order equal id order. `test_ci.py` compares sets, never order.
   - `idempotent` needs a function that moves an entity into a state. The test calls it once, deep-copies the result, records `len(events.OUTBOX)`, calls it again, and asserts that nothing raised, the entity equals the copy, and no event was added. If the function stores a time, move `clock.set_fixed` forward between the calls so a re-stamp shows up. The body never says what a repeat does, and it must not make the target state look invalid (for example, say "a shipment still in status created cannot be marked returned", not "only delivered shipments can be marked returned").
   - `settings` needs a threshold or rate in the body. The test calls `assert_settings(path, function_name, [(value, alternative spelling), ...])`: `parcelo/settings.py` must be created or changed and hold an UPPER_CASE constant equal to each value (give the cents spelling as an alternative for dollar amounts), the module must import `parcelo.settings`, and the function body must contain no numeric literal other than 0, 1, -1 and 100. The seed has no `parcelo/settings.py`, so the gold overlay adds it with only that ticket's constants.
   - `docs_api` is `assert_api_doc("<module>.<function>")` for each new public function the body names. The gold overlay edits `docs/api.md` from the snapshot's version, and the naive overlay leaves it alone. Gold overlays add the doc line for every new public function, listed or not.
5. The naive solution breaks only what the ticket lists. If the ticket does not list `changelog` or `tests`, the conventions test file has no test for it.
6. Keep each solution small, one function or one small module. If the ticket needs a new stored collection, add it to `parcelo/store.py` (and reset it in `reset()`), and say so in the body.
7. Run `.venv/bin/python -m clbench.validate <TICKET-ID>` from the repo root. A ticket is done when it prints `OK`.
